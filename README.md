# Exercise Monitor

Offline, CPU-only full-body movement and exercise monitoring from a single
webcam. Tracks every major joint every frame, recognises the exercise being
performed, counts repetitions, and flags both **angle mistakes** (a joint outside
its safe range for the current phase) and **repetition mistakes** (partial range,
rushed tempo, left/right asymmetry, inconsistent form).

No cloud APIs. No internet access at inference time. No GPU required.

---

## What it actually does, stated plainly

Read this before anything else, because "monitors every exercise" is a claim that
needs qualifying.

**Always works, for any movement at all.** The pose and angle layer is
exercise-agnostic. Every frame, all 33 BlazePose landmarks are extracted and
turned into ~50 whole-body metrics — every joint angle plus normalised distances.
That runs whether the system recognises what you are doing or not.

**Works for movements with a config.** Five ship in `configs/`: squat, push-up,
bicep curl, lunge, shoulder press. For these you get a name, a rep count, and
specific coaching ("Keep your knees aligned with your toes"). Adding a sixth is
one YAML file, no code changes.

**Degrades gracefully for everything else.** Unrecognised movements enter
*generic mode*: joints are still tracked and displayed, repetitions are still
counted (the system auto-selects whichever joint shows the clearest periodic
motion and counts cycles), and exercise-agnostic anomalies are still flagged —
anatomically implausible angles, gross left/right asymmetry, jerky motion. What
it cannot do is tell you your form is wrong for a movement nobody has described
to it, because "correct" is not derivable from video alone.

**What no system of this kind can do**, including this one:

- Have every named exercise pre-loaded with zero setup. That needs either
  training data or a human-authored description of correct form.
- Measure sagittal joint angles from directly in front. A single 2D camera
  projects a squat's knee bend into nothing when you face it head-on. The system
  detects this (`view_frontality`), raises `SUBOPTIMAL_CAMERA_VIEW`, and
  suppresses depth verdicts rather than reporting a number it cannot support.
  **Stand at roughly 45 degrees to the camera.**
- Judge anything it cannot see. Occluded joints produce `NaN`, and every check
  skips `NaN` rather than guessing.

### The numbers, and what they are worth

`docs/metrics_report.md` is generated by `python -m src.evaluate`. Current state:

| metric | target | measured | on what data |
|---|---|---|---|
| Classification accuracy / macro-F1 | >=90% | 99.6% / 99.7% | synthetic |
| Fallback to "unknown" on untrained movements | high | 100% of frames | synthetic |
| Rep-count MAE (exercise forced) | <=1 | 0.02, 100% within +/-1 | synthetic |
| Rep-count MAE (end to end) | <=1 | 0.17, 100% within +/-1 | synthetic |
| Mistake detection precision / recall | >=80% | 99.3% / 100% | synthetic |
| End-to-end throughput | >=15 FPS | **23.1 FPS measured live** (camera-bound) | real, this machine |
| Processing capability | - | ~58 FPS (16.0 ms pose + 3.1 ms analysis) | real, this CPU |
| Startup to first detection | <3 s | ~1.2 s (0.6 s camera + 0.6 s window fill) | real |

**The accuracy figures come from synthetic data and should not be quoted as
real-world performance.** `src/synthetic.py` generates BlazePose-shaped landmark
streams from a 2D forward-kinematic stick figure with a proper camera-azimuth
projection. That is a genuine test bench — it caught several real bugs during
development, listed in `docs/architecture.md` — but it contains no pose-estimation
error model beyond Gaussian jitter, no occlusion, and no out-of-plane movement.
Its "correct form" is whatever its keyframes say. Read those numbers as *"the
logic is correct and the thresholds are consistent"*, not *"99% accurate on
humans"*.

The FPS and latency figures **are** real: measured on this machine with actual
MediaPipe inference. Note the two different numbers. The CPU can process ~58
frames per second, but a live session measured 23.1 FPS because a 640x480 webcam
only delivers ~30 FPS and `read()` blocks waiting for it. **The bottleneck is the
camera, not the analysis** — worth knowing before optimising anything. Check your
own machine with `python -m tools.check_camera`.

To get real accuracy numbers, follow [Recording real
data](#recording-real-data-and-retraining) below. Nothing else needs to change.

## Install and run

Requires Python 3.9–3.12.

```bash
python -m venv .venv
.venv\Scripts\activate          # Windows;  source .venv/bin/activate on Linux/macOS
pip install -r requirements.txt
```

Check your setup first — dependencies, configs, camera, frame rate and camera
angle, all headless:

```bash
python -m tools.check_camera
```

Try it without a camera (replays a recorded session through the full live
pipeline, rendering the skeleton on a blank canvas):

```bash
python -m tools.generate_synthetic_data          # build the dev dataset
python -m src.train                              # ~5 s
python -m src.main --replay data/test_faults/squat_shallow_00.npz
```

Then with a webcam:

```bash
python -m src.main                    # classify automatically
python -m src.main --exercise squat   # skip the classifier, drill one movement
python -m src.main --no-classifier    # generic mode only: pure joint monitoring
```

Keys: `q` quit · `r` reset counters · `a` toggle the angle table · `m` mirror ·
`p` pause · `s` save the current recording.

### Common commands

```bash
python -m src.main --source clip.mp4              # analyse a video file
python -m src.main --benchmark 200                # headless FPS measurement
python -m src.main --model-complexity 0           # BlazePose Lite, for weak CPUs
python -m src.main --save-video out.mp4           # record the annotated output
python -m src.main --fullscreen                   # or press f; --display-width 1600
python -m src.evaluate                            # regenerate the metrics report
python -m pytest tests -q                         # 80 regression tests, ~17 s
```

Diagnostics, for when the live behaviour disagrees with what you did:

```bash
python -m tools.check_camera                      # which camera indices work
python -m tools.check_capture_rate                # true FPS + frame brightness
python -m tools.inspect_reps <session.npz> --exercise bicep_curl
```

`inspect_reps` replays a recording through the real pipeline and prints the rep
signal beside the counter's decisions — when it armed, where it peaked, what the
other joints were doing — so a miscount can be attributed instead of guessed at.
Record a session with `--record <label>` to get one.

The display window is resizable and scaled independently of capture: capture stays
small for speed (`--width`), only the shown copy is enlarged (`--display-width`).

If the camera does not open, try `--source 1` (or 2). On Windows the DirectShow
backend is selected automatically to avoid a multi-second MSMF start-up stall.

## How it works

```
webcam frame
  -> MediaPipe Pose (BlazePose)      33 landmarks, every frame        pose_extraction.py
  -> aspect correction               undo non-square pixel scaling
  -> Universal Angle Engine          ~50 whole-body metrics           angle_engine.py
     (all joints, always, regardless of the exercise)
  -> 5-frame moving average          kills landmark jitter
  -> Exercise classifier             label, or "unknown"              classifier.py
     Random Forest on windowed features, with two rejection gates
  -> Rep counter                     READY -> MOVING_AWAY ->          rep_counter.py
                                     EXTREME -> RETURNING -> +1
     config-driven for known exercises; auto-selected periodic
     signal for unknown ones
  -> Mistake detector                per-frame angle rules +          mistake_detector.py
                                     per-rep verdicts + generic
                                     anomaly checks
  -> Feedback mapper                 error code -> coaching text      feedback.py
  -> Overlay                         skeleton, HUD, angle table       overlay.py
```

`pipeline.py` wires it together and is used by **both** the live loop and the
evaluator, so the metrics report cannot drift away from shipped behaviour.

Full design notes, including the measurement decisions that took real work to get
right, are in [`docs/architecture.md`](docs/architecture.md).

### Metrics the engine produces

Angles in degrees: `knee_l/r`, `hip_l/r`, `elbow_l/r`, `shoulder_l/r`, `ankle_l/r`,
`wrist_l/r`, `body_align_l/r`, `neck`, `torso_lean`, `shoulder_tilt`, `hip_tilt`.

Normalised distances in torso lengths: `knee_valgus_l/r`, `elbow_offset_l/r`,
`wrist_height_l/r`, `hip_height`, `shoulder_height`, `stance_width`,
`shoulder_width`, `hip_drop`, `knee_ankle_ratio`, `view_frontality`.

Every left/right pair automatically gains `<name>_mean` (what rep counting wants)
and `<name>_diff` (what symmetry checks want). Any of these names can be
referenced from a YAML config with no code changes.

### Error codes

| angle mistakes | repetition mistakes | generic mode |
|---|---|---|
| `EXCESSIVE_TORSO_LEAN` | `PARTIAL_REP` | `EXTREME_JOINT_ANGLE` |
| `KNEE_ALIGNMENT_POOR` | `INSUFFICIENT_DEPTH` | `LARGE_ASYMMETRY` |
| `HIP_SAG` / `HIP_PIKE` | `TOO_FAST` / `TOO_SLOW` | `JERKY_MOTION` |
| `ELBOW_FLARE` | `ASYMMETRIC_MOVEMENT` | |
| `SHOULDER_SWING` / `TORSO_SWING` | `INCONSISTENT_FORM` | |
| `NECK_MISALIGNED`, `WRIST_BENT`, `INCOMPLETE_LOCKOUT`, `HIP_HINGE_TOO_EARLY` | | `SUBOPTIMAL_CAMERA_VIEW` |

Codes are structured, not prose. `src/feedback.py` maps them to user-facing text,
so wording (or language, or a TTS voice) changes without touching any logic.

## Adding a new exercise

One YAML file in `configs/`. No code changes. Full walkthrough with a worked
example in
[`docs/adding_a_new_exercise.md`](docs/adding_a_new_exercise.md); the short
version:

```yaml
name: glute_bridge              # must match the filename
display_name: Glute Bridge
tracked_metrics: [hip_mean, knee_mean, torso_lean]

rep_counter:
  primary_metric: hip_mean      # any metric the angle engine emits
  near_threshold: 120           # value at rest
  far_threshold: 165            # value in the worked position
  hysteresis: 7

angle_checks:
  - code: KNEE_ALIGNMENT_POOR
    metric: knee_ankle_ratio
    phases: [extreme]
    min: 0.80
    min_frames: 5
    gates:                      # skip the check when the view can't support it
      - metric: view_frontality
        min: 0.45

rep_checks:
  rom:   { metric: hip_mean, target_extreme: 160, min_range: 35 }
  tempo: { max_speed: 110 }
  symmetry: { pairs: [[knee_l, knee_r]], max_diff: 15 }
```

The loader validates every metric name and fails loudly on a typo rather than
silently ignoring the rule. New exercises get rep counting and mistake detection
immediately. They only get an automatic *name* on screen after you record clips
and retrain the classifier — until then, run with `--exercise glute_bridge`.

## Recording real data and retraining

```bash
# 1. Record. Stand at ~45 degrees to the camera. 20-30 reps per clip.
python -m src.main --record squat --exercise squat --subject alice --expected-reps 20

# Deliberately bad clips for the mistake-detection test set:
python -m src.main --record squat --exercise squat --fault shallow \
    --expected-reps 20 --out-dir data/test_faults

# 2. Retrain (grouped by clip, so overlapping windows cannot leak across the split)
python -m src.train --data data/raw_sessions

# 3. Re-measure
python -m src.evaluate
```

Guidance that matters:

- **Multiple people, camera angles, distances and lighting.** Otherwise you are
  measuring one person in one room.
- **Vary depth and tempo in the training clips**, and include some
  badly-executed reps labelled with the correct exercise name. This is not
  optional: a classifier trained only on textbook reps treats a sloppy rep as a
  *different movement*, its novelty gate rejects it as unknown, and feedback
  switches off for exactly the users who need it. Fixing this took end-to-end rep
  MAE from 1.01 to 0.17 on the bench.
- **Record a "standing still" class** and give it no config. Without an explicit
  rest class the classifier must assign idle frames to some exercise, and the rep
  counter then hunts for reps in the noise.
- **Recalibrate the tempo `max_speed` values** in the configs. The shipped ones
  are derived from synthetic clips and are the numbers most likely to be wrong
  for real footage.
- Recordings store raw landmarks as well as derived metrics, so improving the
  angle engine does not mean re-filming.

`notebooks/training.ipynb` walks through the dataset, features, training and
error analysis interactively.

## Known limitations

1. **Accuracy numbers are from synthetic data.** See above. FPS numbers are real.
2. **Camera angle matters.** ~45 degrees to the subject satisfies both the
   sagittal angle checks and the frontal-plane valgus check. Dead-front and pure
   side views each disable one class of check. The system tells you
   (`SUBOPTIMAL_CAMERA_VIEW`) rather than guessing.
3. **2D only.** BlazePose's `z` is recorded but no form logic uses it: on a single
   webcam it is not stable enough to trust. Projected angles read shallower than
   true anatomical angles in oblique views, and the configured thresholds are
   calibrated against projected values.
4. **Sag vs pike needs a horizontal body.** `hip_drop` is gravity-referenced and
   returns `NaN` for an upright subject, so those checks self-disable. The
   unsigned `body_align` angle cannot distinguish the two directions at all.
5. **One person.** MediaPipe Pose tracks a single subject; the most prominent one
   wins. Multi-person would need a detector plus tracking.
6. **No weight or load awareness.** Bar path, plate counting and equipment are
   out of scope.
7. **`WRIST_BENT` and `HIP_PIKE` are implemented but not covered** by the
   synthetic bench (it has no fault clip that produces them). They are the two
   rules most likely to need adjustment on real footage.
8. **Tempo thresholds are the least transferable setting.** They are angular
   speeds calibrated on synthetic clips; expect to retune them.
9. **The classifier needs ~1 s of video** (a 45-frame window, usable at 60% fill)
   before its first label. Rep counting and joint tracking start immediately.
